# Tornado Product Flow

This document describes how Tornado works from the user's perspective.

It is the source of truth for all user journeys inside the application.

When implementing new features, always preserve these flows.

Never introduce additional screens or unnecessary interactions that increase friction.

---

# Core Philosophy

Every interaction should reinforce three principles.

# Continuous Flow

One of Tornado's core principles is preserving user context.

The player should almost never feel like they are leaving the application flow.

Wallet-related actions are overlays rather than separate pages.

Deposit

Withdraw

History

Bonuses

should open above the current screen instead of replacing it.

Closing an overlay always returns the player to exactly where they were.

No unnecessary navigation.

No page reloads.

No interrupted gameplay.

The player should always feel that Tornado is one continuous experience.

## Speed

The player should reach their goal with the fewest possible interactions.

Open

↓

Play

↓

Leave

The application should always feel responsive.

Avoid unnecessary confirmations.

Avoid unnecessary loading screens.

---

## Simplicity

The interface should never require explanation.

Users should immediately understand:

- where they are
- what they can do
- what happens next

Everything should feel obvious.

---

## Trust

Players should always know:

- current balance
- current game state
- payment status
- bonus progress

The interface should communicate confidence through clarity and consistency.

---

# General Navigation Philosophy

The player should almost never leave the current screen.

Wallet actions are not separate pages.

Deposit

Withdraw

History

Bonuses

should open as fullscreen overlays above the current page.

Closing an overlay always returns the player to the exact previous screen.

# Authentication Flow

Authentication is completely automatic.

The player never sees a login screen.

Flow

Telegram

↓

Open Tornado

↓

Telegram provides InitData

↓

POST /api/auth

↓

Backend validates Telegram user

↓

User exists?

├── Yes
│
│ Load existing account
│
└── No
│
Create new account
│
Generate: - Server Seed - Client Seed - Server Seed Hash - Nonce

↓

Create or refresh server session

↓

Store HttpOnly session cookie

↓

Log Authentication Event

↓

Open Home Page

---

# Session Flow

Every authenticated request follows exactly the same lifecycle.

Request

↓

Read session_token cookie

↓

Validate session

↓

Refresh session activity

↓

Create user event

↓

Execute business logic

↓

Return response

This flow is shared by all authenticated endpoints.

# Product Rules

Every new feature should answer three questions.

Does it make Tornado faster?

Does it make Tornado simpler?

Does it increase player trust?

If the answer is no, reconsider the implementation.

The player should always feel:

"I can do what I came here to do immediately."

That is the primary goal of Tornado.
